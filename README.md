# doc-chat

A small **RAG (Retrieval-Augmented Generation)** learning project built with Node.js, TypeScript and NestJS.

> **In one sentence:** upload documents, embed them locally with Ollama `bge-m3`, retrieve the relevant chunks from PostgreSQL + pgvector, and let DeepSeek answer using only that context.

The idea is to understand each step of RAG without hiding it behind a framework. The project intentionally avoids LangChain, LangGraph, agents, queues, Redis and microservices.

> This is a learning project, not a production-ready system. The basic pipeline through Stage 5 is complete.

## What it does

1. Accepts `.txt`, `.md` and `.markdown` files up to 5 MB.
2. Extracts UTF-8 text and splits it into overlapping chunks.
3. Creates a 1024-dimensional embedding per chunk using **Ollama `bge-m3`**.
4. Stores documents, chunks and vectors in **PostgreSQL + pgvector**.
5. Embeds the question with the same local model and searches by cosine similarity, applying top-k and a minimum score.
6. Builds a prompt with only the retrieved passages and asks **DeepSeek** for a grounded answer.
7. Returns the answer, the supporting source chunks and optional token usage.
8. If no chunk passes the threshold, returns a fixed insufficient-context answer **without calling the LLM**.

Embeddings stay local. Only the question and retrieved passages are sent to DeepSeek for answer generation.

## How RAG works here

```text
INGESTION
file → extract text → chunks → local embeddings → PostgreSQL + pgvector

QUERY
question → local embedding → cosine search → top-k passages
         → grounded prompt → DeepSeek → answer + sources
```

| Concept           | Meaning in this project                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------- |
| **Chunk**         | A small, overlapping piece of a document used for retrieval.                              |
| **Embedding**     | A vector representing the meaning of a text. Similar texts have nearby vectors.           |
| **Vector search** | The question vector is compared with every chunk vector; the closest chunks are returned. |
| **Score**         | Similarity calculated as `1 - cosine distance`. It is not a probability.                  |
| **top-k**         | Maximum number of chunks returned by a search.                                            |
| **Threshold**     | Minimum score a chunk needs to be considered relevant.                                    |
| **Grounding**     | The model is instructed to answer only from the retrieved passages.                       |
| **Sources**       | The original chunks returned by retrieval, not text generated by the model.               |

Defaults:

- chunk size: `1200` characters;
- overlap: `150` characters;
- embedding: `bge-m3`, 1024 dimensions;
- retrieval: top-k `5`, minimum score `0.5`;
- chat: DeepSeek `deepseek-flash`, temperature `0.1`, maximum `1024` output tokens.

The `0.5` threshold was calibrated for this small corpus: relevant passages scored around `0.65–0.69`, irrelevant ones around `0.21–0.29`. Thresholds depend on the model and corpus, so recalibrate after changing either one.

## Why Ollama and `bge-m3`?

Ollama was chosen so embeddings can run **locally**:

- documents are not sent to an external embedding API;
- there is no per-embedding API cost;
- `bge-m3` is multilingual and produces 1024-dimensional vectors;
- Ollama exposes an OpenAI-compatible `/v1` endpoint, so the same `openai` SDK is used for local embeddings and DeepSeek chat.

The trade-off is that Ollama must be running, the model must be installed, and the first request can be slower while the model loads.

```bash
ollama pull bge-m3
ollama list
```

## Why PostgreSQL + pgvector?

pgvector adds a `vector` column type and distance operators to PostgreSQL. This project stores `chunks.embedding` as `vector(1024)` and ranks chunks with the cosine-distance operator `<=>`.

There is no HNSW index yet: the search is an exact scan. It keeps the code simple and gives full recall for a learning-sized corpus. An approximate index is a later optimization.

## DeepSeek

DeepSeek is used only for answer generation, through the OpenAI SDK with a custom base URL:

```env
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash
```

A valid `LLM_API_KEY` is required. Without it, a question with retrieved context returns `503`; a question with no retrieved context still returns the fixed answer without calling the LLM. The key stays on the server and is never sent to the frontend.

## Database

The migrations enable the `vector` extension and create two tables:

```text
documents
  id          uuid, primary key
  filename    text
  mime_type   text
  content     text          -- extracted full text
  created_at  timestamptz

chunks
  id          uuid, primary key
  document_id uuid, foreign key → documents(id), ON DELETE CASCADE
  chunk_index int
  content     text
  embedding   vector(1024)
  created_at  timestamptz

  UNIQUE (document_id, chunk_index)
  INDEX  (document_id)
```

`GET /documents` lists metadata only, without the full content. Chunks and vectors are stored transactionally during upload.

Changing the embedding model or dimension requires a new migration and reindexing, because the `vector(1024)` column is fixed.

## Run locally

Prerequisites:

- Node.js 24+
- npm
- Docker Desktop
- Ollama running at `127.0.0.1:11434`
- the `bge-m3` model installed
- port `5432` available, or a different `DB_PORT`

```bash
cp .env.example .env

npm install
ollama pull bge-m3
docker compose up -d
npm run migration:run
npm run start:dev
```

Open `http://localhost:3000`. The minimal English interface has a chat and a Documents view.

Check the API and database:

```bash
curl http://localhost:3000/health
```

```json
{
  "status": "ok",
  "db": "up",
  "pgvector": "0.8.7"
}
```

The pgvector version can vary with the Docker image.

To enable chat, set a valid key and restart the API:

```env
LLM_API_KEY=your-deepseek-key
```

Upload, embeddings and retrieval work without this key.

## API

| Method | Endpoint            | Description                                                   |
| ------ | ------------------- | ------------------------------------------------------------- |
| `GET`  | `/health`           | Checks PostgreSQL and the `vector` extension.                 |
| `POST` | `/documents`        | Uploads a file, extracts text, chunks, embeds and stores it.  |
| `GET`  | `/documents`        | Lists document metadata, newest first.                        |
| `POST` | `/retrieval/search` | Semantic search without an LLM; useful for inspecting scores. |
| `POST` | `/chat`             | Retrieves context, builds the prompt and calls DeepSeek.      |

Upload is synchronous: the response arrives after chunking and embeddings finish. If Ollama is unavailable, the upload returns an error and nothing is persisted.

Example chat request:

```bash
curl -X POST http://localhost:3000/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"What are the payment terms in the contract?"}'
```

Response shape:

```json
{
  "answer": "The contract states that payment is due within 30 days. [1]",
  "sources": [
    {
      "chunkId": "...",
      "documentId": "...",
      "filename": "contract.txt",
      "chunkIndex": 3,
      "content": "Payment is due within 30 days of invoice receipt.",
      "score": 0.68
    }
  ],
  "usage": {
    "inputTokens": 420,
    "outputTokens": 32
  }
}
```

`sources` comes from retrieval, not from the model. A citation such as `[1]` is a convenience; the structured `sources` array is the reliable provenance.

There is no streaming and no conversation memory: each question is independent. If retrieval returns `[]`, the answer is the fixed insufficient-context message and `usage` is absent.

## Frontend

The frontend is served by Nest at `http://localhost:3000`; there is no separate server or CORS setup.

- **Chat:** calls `POST /chat`, renders paragraphs/lists, turns `[1]` citations into source links and shows each source with an expandable **Quoted passage**.
- **Documents:** uploads files, lists persisted documents and exposes a semantic-search form for `POST /retrieval/search`.
- **New chat** is disabled when there is no conversation and while a request is running.

Do not open the HTML as `file://`; use the URL served by Nest.

## Limitations and next steps

This project intentionally stops at a basic RAG pipeline. It does not include streaming, conversation history, reranking, hybrid search, an HNSW index, citation validation, authentication, rate limiting or automated evaluation.

Other limitations:

- the threshold depends on the embedding model and corpus;
- prompt injection through documents is mitigated by instructions, not fully prevented;
- the threshold can reject an answerable question;
- uploads are synchronous and the first Ollama request can be slow.

The next useful step is evaluation: create a small golden set of question → expected chunk, then experiment with chunk size, overlap, top-k and threshold. Approximate indexes, hybrid search and reranking can be studied after the baseline is measured.
